## Context

仓库原技术基线是微信小游戏原生 JavaScript + Canvas 2D，包含主页、游戏、结算、开放数据域、广告、分享、声音和本地存储，并叠加了约 2500 行未提交修改与 11 个未归档 OpenSpec 变更。用户已明确这些旧成果不需要提交、备份或迁移。

新的产品交接文档改变了目标：竖屏、单手、1—3 分钟单关，核心差异化来自连锁反应、每三回合能力三选一、每日同图和轻量收集成长；原型阶段不做复杂排行、成就、商城和广告。文档同时建议先用独立 Figma 文件验证流程，再创建 Cocos Creator/TypeScript 工程。

## Goals / Non-Goals

- Goals:
  - 建立唯一、可执行的产品基线。
  - 彻底移除与新方向冲突的旧实现，避免双基线并存。
  - 将 Figma、灰盒、MVP 内容和上线准备拆成独立验收阶段。
  - 控制个人开发项目的范围和维护成本。
- Non-Goals:
  - 本提案不直接创建 Figma 文件。
  - 本提案不直接创建 Cocos Creator 工程。
  - 本提案不迁移旧存档、排行榜或广告数据。
  - 本提案不实现实时多人、复杂商城、公会或大型成就系统。

## Decisions

### Decision: 直接删除旧原型，不建立快照

用户已明确旧代码不需要考虑提交或保留。本次直接删除原生 Canvas 运行时、旧资源、旧配置、旧说明和旧 OpenSpec，不创建分支、提交或补丁，也不迁移旧存档数据。

Alternatives considered:

- 保存旧代码后再删除：保留回退能力，但用户已明确不需要，且会增加无价值的维护负担。
- 继续在原生 Canvas 工程上改造：短期复用较多，但会把产品换轨和引擎换轨耦合在一起。

### Decision: 新工程不复用旧运行时代码

Phase A 验证通过后新建 Cocos Creator/TypeScript 灰盒。玩法规则以产品规格重新定义，不复制旧 UI、增长系统、配置或运行时代码。

### Decision: Figma 是进入工程开发的门禁

Phase A 先完成产品说明、用户流程、低保真页面、核心游戏界面高保真和可点击主流程。只有核心流程、页面信息层级和竖屏操作区域获得确认，才进入 Cocos 灰盒。

### Decision: 主界面高保真以四个可验证状态表达

游戏主界面不只展示静态默认态，而是用“瞄准准备、连锁爆发、三回合进化、危险与召回”四个 375×812 状态覆盖核心决策与反馈峰值。信息优先级固定为“目标 → 回合/进化 → 连锁 → 能力 → 操作”，避免把章节、体力、能力和操作提示压成同一层级。

底部 176px 作为单手拇指操作区：当前状态的主操作不小于 72px，次操作不小于 48px；进化选项整卡可点。关键反馈不得只依赖颜色，目标色调同时使用形状与血量文字，连锁和危险状态同时使用色彩、符号与数值/文案。高保真方案复用基础变量和轻量组件，并通过顶层画板间的原型跳转验证“发射 → 连锁 → 进化 → 回到瞄准”以及危险召回分支。

### Decision: “夜游奇境 · 国风霓虹弹射”是 Phase A 视觉与体验验收基线

Figma 不得只验证静态页面结构，还必须表现“平静 → 瞄准 → 期待 → 连锁 → 高潮 → 收束 → 奇遇 → 决策 → 再次平静”的完整情绪曲线。世界壳保持治愈萌系与轻国潮，战斗场改为深靛夜色；玉色、鎏金和珊瑚高亮只用于弹珠、目标、轨迹、连锁和关键 CTA。云、水、山、月、植物和玉石继续采用现代化、几何化表现，避免照搬纯工业霓虹、科幻 HUD 或竞品广告大厅。

首页必须在 1 秒内回答“这是什么玩法、为什么现在要玩”：展示可感知的弹射场、当前章节进度和主要奖励，并以一个强主 CTA 进入关卡；次级入口最多两个，原型阶段不得用 VIP、广告奖励、排行榜轰炸制造虚假吸引力。

主游戏区域必须成为第一视觉焦点，清晰竞技场边界、可辨耐久数字和目标状态用于降低理解成本，UI 在发射后主动弱化。玩家弹珠采用“70% 弹珠 + 30% 小生命感”，目标物使用圆、三角、菱形等奇境符印轮廓与数值整合，不得退化为带血量数字的纯色胶囊。连锁反馈必须覆盖普通碰撞、连续碰撞、明显连锁和整屏连锁四级；整屏连锁可以强烈，但必须保留竞技场、弹珠和目标的空间关系，并在高潮后快速恢复清爽状态。

“每三回合三选一”统一使用“奇遇降临”的世界观表达。三个能力必须在 3 秒内可理解，并避免 SSR 卡牌、复杂金边、稀有度轰炸和传统手游大厅感。所有方案同时满足微信右上角胶囊、顶部与底部安全区、单手操作、40 岁左右用户可读性和中低端安卓性能约束；原型效果应能用少量序列帧、渐变、描边和对象池实现，不依赖持续全屏粒子或实时重模糊。

### Decision: V4 采用“游戏画面优先”的三色纠偏规则

用户否决 V3 的主要原因是视觉层级混乱，而不是信息缺失。V4 不再让多个描边卡片、状态标签和高亮颜色同时争夺注意力。页面使用深紫黑与白灰作为中性色；青色只表示玩家弹珠和轨迹，黄色只表示目标、命中与主 CTA，红色只表示危险、失败和不可越界状态。静态页面不得同时出现第四种高饱和玩法色。

首页以真实主视觉、品牌标题和一个大 CTA 形成单一阅读路径。除微信胶囊外，首页强描边容器不得超过两个；次级入口继续最多两个，但必须降为文字或单色图标，不得与 CTA 竞争。

战斗页只常驻比分、回合、竞技场、目标和弹珠。竞技场使用两条边界轨道而不是大卡片套小卡片；状态说明、预计反弹、奖励承诺等信息仅在必要时短暂出现。整屏连锁通过轨迹、碎片、目标破裂和顶部小型连击数表达，不得在竞技场中央放置大字、圆环或遮罩。任一瞬间的反馈都必须保留目标位置、弹珠运动方向和可玩区域。

V4 先只重做首页、瞄准和整屏连锁三张标杆页。三张页面通过用户视觉评审前，不迁移其余八张流程页，也不删除 V3。

### Decision: 灰盒只验证一个核心闭环

首个灰盒只包含瞄准、轨迹预览、顺序发射、反弹、碰撞、消除、回收、回合推进、胜负、一种分裂能力、一种连锁能力，以及快进/召回。其他内容全部延后。

## Risks / Trade-offs

- Figma 先行会推迟编码开始时间，但能显著减少个人开发者在不熟悉 UI/UX 和 Cocos 时的返工。
- 轻国潮场景与四级连锁会增加原型状态数量，但可以提前暴露美术资源、动效和性能风险，避免把静态 UI 误判为核心体验已经成立。
- 三色规则会牺牲部分世界装饰的色彩丰富度，但能确保玩家在一眼内区分自己、目标和危险，并降低中低端设备上的光效成本。
- 放弃直接演进旧原型会减少代码复用，但能避免把旧的无尽模式、广告和增长系统带入新架构。
- 每日同图和排行榜最终需要服务端校验；MVP 初期可本地演示，但不可把本地结果视为可信竞技数据。
- 固定时间步与高速连续碰撞会增加物理实现复杂度，需要独立的自动模拟和真机性能验证。

## Migration Plan

1. 删除旧运行时代码、资源、微信项目配置、说明和 OpenSpec 历史。
2. 更新仓库根文档与 OpenSpec 项目上下文，使新基线成为唯一事实。
3. 执行 Phase A 独立 Figma 设计与评审。
4. Phase A 通过后，另建 OpenSpec 变更启动 Cocos Creator/TypeScript 灰盒。
5. 灰盒真机验证通过后，再按功能垂直切片扩展 MVP。
