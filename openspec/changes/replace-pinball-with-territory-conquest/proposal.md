# Change: 在当前项目以据点争夺替代弹球方向

## Status

2026-09-08，v0.2：**产品转向及本轮文档细化已由用户提出；具体玩法与实施顺序待批准；运行时未开工。**

本版依据用户关于最后城池与据点等级的讨论细化推荐方案，但“是否更合理”的讨论及“细化文档”的请求不等于规则已经获批。详细规则见 [design.md](design.md)，配套 [关卡与电脑](appendices/levels-and-ai.md)、[界面动效](appendices/interface-and-motion.md)、[验收用例](appendices/acceptance.md)。

已执行的仓库整理不等于玩法已实现：旧弹球资料退役、入口切换，保留原始文件以免覆盖已有未提交工作。用户没有要求新建项目、恢复旧缓存、修改 Figma 或提交代码，本轮均不执行。

## Why

用户明确放弃“弹弹奇境”的弹球制作，并要求在当前项目直接调整。新提供的参考截图和历史素材指向产兵、派兵、增援、占领据点的轻量策略玩法。当前没有新的策划文档，因此需要建立一份小而明确的新方案，不能把历史三兵种、锦囊、四人房间或助手提出的玩具风格自动当作定稿。

当前仓库无可运行游戏代码。方向切换与旧资料退役已完成，本轮补充详细设计与一致的需求场景；等待新规则批准后再创建最小可玩版本。

## What Changes

- **BREAKING**：取消弹球产品名、反弹消除、符印/灵球、三回合强化与旧 Phase A 制作任务作为当前基线。
- 在原仓库继续，不另开工程目录或任务，不恢复外部 Cocos 预览缓存。
- 将旧弹球入口、活动变更和专属素材原样迁至 `docs/history/retired-pinball-2026-09-08/`；这不是已完成功能归档。
- 提议首版为单机玩家对一个电脑，采用自动产兵、拖拽派出一半兵力、支援/攻占及明确胜负规则。
- 提议 M0 先用第一关与兵营 I 实现操作闭环；M1 再扩展完整三关、兵营/堡垒/驿站各两级，仍只有一种基础兵力。等级地图预设，不做局内升级、克制或卡牌。
- 草案推荐“最后一城被攻占即淘汰”，在途部队不能续命；精确同一游戏毫秒双方失去全部原有据点时判平局。这替换 v0.1 在途反攻续命规则，但仍待用户确认。
- 明确生产/派兵/到达的时序、同刻兵团合并、容量舍弃、输入取消、三张地图坐标和电脑参数，提供页面动效与分阶段测试用例。
- 将“夺城接力”作为后续可开关实验，不与基础玩法同时强制上线；不宣称市场独有或已证明好玩。
- 只借鉴参考的核心操作思路，重新建立视觉表达；旧水墨素材及旧弹球夜色玉石风格均不直接成为新美术基线。
- 保留轻量本地数据与微信官方好友周榜例外；榜单接入后置，计分重新设计。
- 提议用“规则确认 → 可玩小样 → 单机制实验 → 正式视觉与 Figma → 微信真机/MVP”替代旧弹球全套 Figma 前置流程。

## Impact

- Affected specs：新增提案能力 `territory-battle`、`lightweight-game-scope`。当前 `openspec/specs/` 为空，所以不伪造对已实现弹球能力的删除 delta。
- Affected files：根 `readme.md`、`openspec/project.md`、旧活动提案和 `design-assets/` 的位置，以及本变更目录。
- Future code：批准后新建规则、配置、渲染/输入、最小电脑对手及测试；现阶段没有可运行工程或构建链。
- Unaffected：Git 历史、用户外部材料、远端 Figma、微信数据和其他项目。
- Data migration：无新存档写入，不读取或迁移旧存档；未来使用独立版本化存档格式。

## Approval Requested

请确认是否按以下首版范围进入运行时制作：

1. 单机对一个电脑、一种基础兵力；M0 第一关先验证，M1 完成三关及三类据点各两级。
2. 自动产兵，拖拽派出一半兵力，到达后增援或扣减守军；中立据点不是必占目标。
3. 最后一城被攻占即淘汰，不等待在途部队；精确同刻双方失去全部原有据点时判平局，同批新夺据点不抵销淘汰。
4. 同量交战归属保留、战斗后超容量舍弃、同刻事件按主文档统一结算；先验证可玩，不先制作全套页面。
5. 据点等级由地图预设，不做手动升级；夺城接力单独决定，三兵种/肉鸽/周榜不自动纳入本次批准范围，正式名称和视觉另定。

本提案中的数量、速度和时间均为初始试验参数，不是已经平衡的上线值。正式名称和视觉主题不阻塞规则原型，可随后单独确认。
